# 15 · 阶段九：买家端与交易闭环（学习规划）

> 定位：阶段八完成的是一个「店家后台」——店家登录、管理商品、下单、模拟支付。阶段九补上买家侧，把「浏览商品 → 加购物车 → 下单 → 支付 → 发货 → 收货 → 售后」串成完整闭环。
>
> 前置：阶段八全部完成（JWT 鉴权、A-5 越权控制、Redis 缓存、Swagger、打包运行）。
>
> 建议节奏：4 个里程碑，每个约 1 周，可按自己的时间调整；每个里程碑都要有可运行的接口和自动化测试，不追求一次做完。

## 一、为什么要做这个阶段

现在的订单是店家自己创建的，买家姓名和电话只是手填文本，支付也由店家发起。这在学习阶段能跑通，但不是真实的电商链路。

阶段九要回答几个新问题：

- 买家和店家是两种身份，JWT 如何区分角色？
- 买家如何浏览所有店家的上架商品，而又不能看到下架商品？
- 购物车放在数据库还是 Redis？价格和库存以哪个为准？
- 一次结算包含多个店家的商品时，订单怎么拆？
- 支付后订单如何从「待发货」走到「已发货」「已完成」？
- 买家和店家各自只能操作哪些数据？

这些问题覆盖了账户体系、权限模型、交易状态机、数据快照和并发校验，是后端业务能力的一次明显升级。

## 二、当前基础与缺口

| 能力 | 阶段八结束时 | 阶段九需要补上 |
| --- | --- | --- |
| 账户 | 只有 `merchant` 店家表 | 新增买家账户，JWT 区分 `MERCHANT` / `BUYER` |
| 商品浏览 | 商品详情只允许所属店家查看（A-5） | 新增买家侧公开商品目录，只展示上架商品 |
| 下单 | 店家创建订单，买家信息是手填文本 | 买家从购物车结算，订单关联 `buyer_id` 和收货地址快照 |
| 支付 | 店家对自己的订单发起支付 | 买家对自己的订单发起支付 |
| 订单状态 | 0 待支付、1 已支付、2 已取消 | 增加已发货、已完成，以及可选的退款状态 |
| 履约 | 无发货/收货 | 店家发货、买家确认收货、状态历史 |
| 权限 | 店家只能操作自己的商品/订单 | 增加买家数据隔离和角色访问控制 |

> 分类仍然是全局目录；阶段九可以先不做分类归属，把精力放在买家与交易链路上。

## 三、数据模型设计

### 1. 新增表

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `buyer` | `id`、`username`、`password`、`nickname`、`phone`、`status`、`create_time` | 买家账户，密码同样用 BCrypt |
| `buyer_address` | `id`、`buyer_id`、`receiver_name`、`phone`、`province`、`city`、`district`、`detail`、`is_default` | 收货地址，只能操作自己的地址 |
| `cart_item` | `id`、`buyer_id`、`product_id`、`quantity`、`create_time`、`update_time` | 购物车；对 `(buyer_id, product_id)` 建唯一索引，重复添加则累加数量 |
| `order_status_history` | `id`、`order_id`、`from_status`、`to_status`、`operator_type`、`operator_id`、`remark`、`create_time` | 订单状态流转记录，方便排查和展示物流进度 |
| `refund_request`（可选） | `id`、`order_id`、`buyer_id`、`reason`、`amount`、`status`、`create_time`、`handle_time` | 退款申请；放到最后一个里程碑，做不完可以延后 |

### 2. 修改订单表

给 `order` 表增加：

- `buyer_id`：下单买家；
- `receiver_name`、`receiver_phone`、`receiver_address`：收货信息快照；
- `ship_time`、`receive_time`：发货/收货时间；
- 状态字段扩展，但**不要重排已有状态值**，避免旧数据和旧测试全部失效。

建议状态值：

| 值 | 含义 | 触发方 |
| --- | --- | --- |
| 0 | 待支付 | 买家下单 |
| 1 | 已支付 / 待发货 | 支付回调 |
| 2 | 已取消 | 买家在待支付时取消（保留原值） |
| 3 | 已发货 | 店家发货 |
| 4 | 已完成 | 买家确认收货 |
| 5 | 退款中（可选） | 买家申请退款 |
| 6 | 已退款（可选） | 店家同意退款 |

实现时建议用 `OrderStatus` 枚举替代散落的数字，避免 `status == 3` 这种魔法值越来越多。

### 3. 结算与拆单

购物车可以包含多个店家的商品，但现有 `order` 表只有一个 `merchant_id`。推荐规则：

> **一次结算按店家拆成多张订单**：同一店家的商品生成一张订单，每张订单独立支付、发货和确认收货。

例如购物车里有 A 店 2 件、B 店 1 件，结算后生成两张订单。整个结算放在一个事务里：任意商品库存不足或下架，全部回滚，避免只成功一半。

如果觉得拆单太复杂，可以先限制「一次只能结算同一家店的商品」，把多店拆单放到后续迭代；但不建议把多个店家的商品塞进一张订单，否则订单归属和发货都会变复杂。

### 4. SQL 迁移

新增 `mall/sql/06-阶段九-买家端.sql`，包含建表、加字段和索引；同步更新 `05-测试库初始化.sql` 或说明如何在 `mall_test` 执行新脚本。学习阶段先继续用 SQL 文件管理变更，等表结构稳定后再考虑 Flyway。

## 四、身份与权限设计

### 1. JWT 增加角色

现在 token 里只有店家 ID。阶段九建议改为：

```text
role      = MERCHANT | BUYER
subjectId = 店家 ID 或买家 ID
```

为了兼容阶段八，可以保留 `merchantId` claim：店家 token 同时带 `role=MERCHANT` 和 `merchantId`；买家 token 带 `role=BUYER` 和 `buyerId`。

拦截器校验通过后，把 `role` 和 `subjectId` 放进 request attribute。Controller 不读取请求体或 URL 里的用户 ID，仍然遵循 A-5 的原则：**身份只从 token 来**。

### 2. 接口分区

为了不推翻现有接口，路径可以这样安排：

| 前缀 | 使用者 | 说明 |
| --- | --- | --- |
| `/api/shop/**` | 所有人（可匿名） | 公开商品目录，只返回上架商品 |
| `/api/buyers/**` | 买家 | 注册、登录 |
| `/api/buyer/**` | 买家 | 地址、购物车、买家订单、支付、确认收货 |
| `/api/**` 现有接口 | 店家 | 商品管理、订单管理、发货、统计 |

拦截器按路径和角色校验：买家访问店家接口返回 403，店家访问买家接口同样返回 403。支付回调继续保持公开，靠验签（真实项目）而不是 JWT。

### 3. 公开商品目录

A-5 让商品详情只对所属店家开放，但买家需要浏览所有上架商品。建议新增：

- `GET /api/shop/products/page`：只查 `status=1` 的商品，支持关键字、分类、价格排序；
- `GET /api/shop/products/{id}`：商品下架或不存在时都返回「商品不存在」，不暴露下架商品；
- 复用商品详情缓存，但公开读取和店家读取使用不同的可见性规则：缓存命中后，公开接口仍要检查 `status=1`，店家接口仍要检查归属。

## 五、API 规划

### 买家账户与地址

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/buyers/register` | 买家注册 |
| POST | `/api/buyers/login` | 买家登录，返回买家 token |
| GET | `/api/buyer/addresses` | 我的地址列表 |
| POST | `/api/buyer/addresses` | 新增地址 |
| PUT | `/api/buyer/addresses/{id}` | 修改自己的地址 |
| DELETE | `/api/buyer/addresses/{id}` | 删除自己的地址 |
| PUT | `/api/buyer/addresses/{id}/default` | 设为默认地址 |

### 购物车

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/buyer/cart` | 查看购物车，返回当前价格、库存和是否上架 |
| POST | `/api/buyer/cart/items` | 加入购物车；已存在则累加数量 |
| PUT | `/api/buyer/cart/items/{productId}` | 修改数量 |
| DELETE | `/api/buyer/cart/items/{productId}` | 删除一项 |
| DELETE | `/api/buyer/cart` | 清空购物车 |

> 购物车不保存「下单时的价格」，展示和结算都以商品当前价格为准；订单明细才保存价格快照。结算时必须重新校验库存和上架状态，不能信任加购时的数据。

### 买家订单与支付

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/buyer/orders/checkout` | 从购物车结算，按店家拆单，扣库存，清空已结算项 |
| GET | `/api/buyer/orders/page` | 我的订单分页 |
| GET | `/api/buyer/orders/{id}` | 我的订单详情 |
| PUT | `/api/buyer/orders/{id}/cancel` | 待支付订单取消 |
| POST | `/api/buyer/orders/{id}/pay` | 买家发起模拟支付 |
| GET | `/api/buyer/orders/{id}/pay-status` | 查询支付状态 |
| PUT | `/api/buyer/orders/{id}/confirm` | 确认收货（已发货 → 已完成） |

### 店家履约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/orders/page` | 店家查看自己的订单（已有） |
| PUT | `/api/orders/{id}/ship` | 已支付订单发货 |
| PUT | `/api/orders/{id}/refund/approve` | 同意退款（可选） |
| PUT | `/api/orders/{id}/refund/reject` | 拒绝退款（可选） |

所有接口都从 token 取当前用户，订单/地址/购物车操作必须校验归属；跨用户访问返回 403。

## 六、分里程碑实施

### 里程碑 1：买家账户与公开商品

- 新建 `buyer` 表、买家注册/登录；
- 扩展 JWT：`role` + `subjectId`，兼容现有店家 token；
- 新增 `/api/shop/**` 公开商品接口，只返回上架商品；
- 买家地址 CRUD + 归属校验；
- 测试：买家登录、角色隔离、公开商品不返回下架商品、地址跨用户 403。

### 里程碑 2：购物车与结算

- 新建 `cart_item` 表，完成购物车增删改查；
- 加入购物车时校验商品存在、上架、库存（最终以下单时为准）；
- 结算流程：读取购物车 → 按店家分组 → 校验价格/库存 → 生成订单和明细快照 → 扣库存 → 清空已结算购物车；
- 订单增加 `buyer_id` 和收货地址快照；
- 测试：重复加购累加、跨买家隔离、库存不足全部回滚、按店家拆单、结算后购物车清空。

### 里程碑 3：支付与履约

- 买家对自己的订单发起支付；
- 店家对已支付订单发货；
- 买家确认收货；
- 新增 `order_status_history`，记录每次状态流转；
- 状态机校验：未支付不能发货、未发货不能确认收货、已取消不能支付；
- 测试：完整链路、错误状态流转、跨店家操作 403。

### 里程碑 4：售后、文档与回归

- 可选：退款申请、店家同意/拒绝、订单退款状态；
- 更新 Swagger 注解和 `.http` 主链路脚本；
- 补齐买家端集成测试，跑全量回归；
- 更新 README、测试清单和阶段九文档；
- 重新打包验证，确认买家端与原有店家端可以一起运行。

## 七、测试计划

建议新增 `BuyerAuthTest`、`AddressControllerTest`、`CartControllerTest`、`BuyerOrderControllerTest`、`OrderFulfillmentTest` 等测试类，重点覆盖：

- 买家注册/登录、JWT 角色正确；
- 店家 token 不能访问买家接口，反之亦然；
- 公开商品只展示上架商品；
- 购物车只能操作自己的数据；
- 结算价格和库存以数据库为准，客户端传的价格无效；
- 库存不足时订单、明细、库存、购物车全部不变；
- 多店家结算拆单正确；
- 买家不能查看/取消/支付别人的订单；
- 店家不能给其他店家的订单发货；
- 状态机非法流转被拦截；
- 退款（如果实现）不能超过实付金额、不能重复退款。

目标是在现有 77 条测试基础上新增 25~35 条，保持全量测试可重复、每个用例前后数据隔离。

## 八、验收清单

完成阶段九时，应该能演示这条完整链路：

1. 买家注册、登录，拿到买家 token；
2. 买家浏览公开商品，只能看到上架商品；
3. 买家新增收货地址，加入购物车；
4. 买家结算，按店家生成订单，库存扣减，购物车清空；
5. 买家支付自己的订单；
6. 店家只能看到并给自己店家的订单发货；
7. 买家确认收货，订单变为已完成；
8. 买家 A 不能访问买家 B 的地址、购物车和订单；
9. 店家 A 不能操作店家 B 的订单；
10. 全量测试通过，`mvn clean package` 成功，Swagger 和 `.http` 脚本同步更新。

## 九、暂不做的内容

为了避免阶段九无限膨胀，以下内容先不做，留到后续阶段：

- 真实支付、退款通道和物流接口；
- 优惠券、满减、积分；
- 多级分类、SPU/SKU、规格库存；
- Elasticsearch 搜索；
- 消息队列、分布式锁、分库分表；
- 管理员后台和完整 RBAC 权限系统。

这些方向可以在买家交易闭环跑通后再逐个加入，避免同时引入太多新概念。

## 十、下一步

建议从**里程碑 1**开始：先设计 `buyer` 表、扩展 JWT 角色、增加公开商品接口。第一步只做账户和公开浏览，不碰购物车和订单，这样能先把「买家身份 + 角色隔离」这条基础打牢。

开始实现前，先确认两个设计选择：

1. 结算是否按店家拆单（推荐拆单）；
2. 退款是否放在阶段九最后一个里程碑（推荐放，但可以标记为可选）。
