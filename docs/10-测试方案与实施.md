# 10 · 测试方案与实施

> 目标：给已经写完的接口补上自动化测试，让「改坏了」这件事在 `mvn test` 里立刻暴露，而不是靠手点接口才发现。
> 验收标准：`mvn test` 全绿；能说清三层测试各自解决什么问题，以及为什么这个项目以集成测试为主力。

写测试容易走向两个极端：一行不写，全靠手工点；或者一上来就追覆盖率，把时间花在测 getter 上。这篇文档走的是中间路线——用尽量少的测试代码，守住这个项目最容易出错的那一层。先讲选型，再落到具体写法和运行方式。

## 一、选型：三层测试，主力放在集成测试

三层测试各有分工，本项目对它们的用量差别很大：

| 层级 | 技术 | 能覆盖什么 | 本项目用量 |
| --- | --- | --- | --- |
| 集成测试 | `@SpringBootTest` + MockMvc + 真实 MySQL | 路由、参数校验、统一返回结构、事务回滚、SQL 正确性 | **主力** |
| 单元测试 | JUnit 5 + Mockito，不启动容器 | 纯逻辑分支、异常抛出、调用次数校验 | 少量 |
| 接口脚本 | `.http` 文件（JetBrains HTTP Client 格式） | 手工回归、调参、演示 | 补充（见 [12](./12-HTTP接口测试脚本使用说明.md)） |

### 为什么主力不是单元测试

单元测试的价值在于「隔离」：把依赖换成假对象，只盯着被测方法内部的分支。问题在于，回顾这个项目一路踩过的坑，绝大多数错误并不在算法里，而在「框架 + 数据库」的接缝处。把这些 Mapper 换成假对象之后，反而恰好绕开了最容易出问题的地方：

| 踩过的坑 | 单元测试能发现吗 | 原因 |
| --- | --- | --- |
| `order` 表名不加反引号导致 SQL 语法报错 | 不能 | Mapper 是假的，SQL 根本没发出去 |
| 驼峰字段与下划线列的映射、`BigDecimal` 类型不匹配 | 不能 | 映射发生在 MyBatis 层，mock 里不存在 |
| `@Transactional` 到底有没有真的回滚 | 不能 | 事务由容器管理，假对象没有事务 |
| 原子扣减 `WHERE stock >= quantity` 是否真能防超卖 | 不能 | 要真实数据、真实并发才能验证 |
| `@Valid` 是否生效、返回是不是统一的 `Result` 结构 | 不能 | 属于 web 层行为，只有 MockMvc 看得到 |

结论：**这个项目最容易出错的是「框架 + 数据库」这一层，不是算法层。** 把依赖 mock 掉的单元测试，恰好测不到最需要保障的部分。所以主力放在集成测试，单元测试只留给完全不碰数据库的纯逻辑。

> 前端视角：单元测试像给单个工具函数写测试，跑得快但覆盖窄；集成测试像拿真实后端跑一遍完整请求链路，慢一些，但覆盖的正是你怀疑会坏的地方。

## 二、技术栈：依赖已经就绪

`pom.xml` 里已经有 `spring-boot-starter-webmvc-test`（test 作用域），不用再添加任何依赖。它带齐了下面这些能力：

| 库 | 作用 |
| --- | --- |
| JUnit 5 | 测试框架：`@Test`、`@BeforeEach`、`assertThrows` |
| Mockito | 造「假的」依赖对象，用于纯单元测试 |
| AssertJ | 链式断言：`assertThat(...).isEqualTo(...)` |
| Spring Test | `@SpringBootTest`、`@ActiveProfiles`、`MockMvc` |
| JsonPath | 断言 JSON 响应里的具体字段：`jsonPath("$.code")` |

## 三、测试库必须隔离：用 mall_test，不要用 H2

绝不能让测试跑在开发库 `mall` 上。测试会清库、造脏数据，跑一次就把你手工准备的数据冲掉了。所以测试连的必须是另一个库。

**建库脚本**：`mall/sql/05-测试库初始化.sql`（建 `mall_test` 库 + 5 张表，只需执行一次）

**测试专用配置**：`mall/src/test/resources/application-test.yml`

```yaml
spring:
  datasource:
    url: "jdbc:mysql://localhost:3306/mall_test?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai"
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:}
    driver-class-name: com.mysql.cj.jdbc.Driver
```

测试基类用 `@ActiveProfiles("test")` 激活这个 profile，跑测试时数据源就自动指向 `mall_test`，开发库完全不受影响。

### 为什么不用 H2 内存库

H2 常被拿来做测试库——不用装数据库、启动还快——但它和 MySQL 的方言差异，恰好都落在这个项目的痛点上：

| 差异点 | 影响 |
| --- | --- |
| 反引号表名 `` `order` `` | H2 兼容模式行为不同，在 H2 上测过了不代表 MySQL 能跑 |
| `ON DUPLICATE KEY UPDATE`、`LIMIT` 等语法 | 语法支持不一致 |
| `DECIMAL` 精度、自增回填行为 | 可能与 MySQL 有细微差别 |

一句话：**在 H2 上测出来的绿色，不能证明 MySQL 上也是好的。** 本项目宁可多装一个库，也要让测试跑在和生产一致的 MySQL 上。

## 四、测试代码怎么写

### 1. 基类：把「起容器、连测试库、清数据」收在一处

所有集成测试都继承这个基类，公共准备只写一遍：

```java
package com.mall.mall.support;

import com.mall.mall.mapper.CategoryMapper;
import com.mall.mall.mapper.MerchantMapper;
import com.mall.mall.mapper.OrderItemMapper;
import com.mall.mall.mapper.OrderMapper;
import com.mall.mall.mapper.ProductMapper;
import org.junit.jupiter.api.BeforeEach;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc;
import org.springframework.context.annotation.Import;
import org.springframework.test.context.ActiveProfiles;
import org.springframework.test.web.servlet.MockMvc;

@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
@Import(MockMvcUtf8Config.class)
public abstract class BaseIntegrationTest {

    @Autowired
    protected MockMvc mockMvc;

    @Autowired
    protected MerchantMapper merchantMapper;

    @Autowired
    protected CategoryMapper categoryMapper;

    @Autowired
    protected ProductMapper productMapper;

    @Autowired
    protected OrderMapper orderMapper;

    @Autowired
    protected OrderItemMapper orderItemMapper;

    @BeforeEach
    void cleanDatabase() {
        // 专职测试库，直接清空，保证每个用例从零开始
        orderItemMapper.delete(null);
        orderMapper.delete(null);
        productMapper.delete(null);
        categoryMapper.delete(null);
        merchantMapper.delete(null);
    }
}
```

这段代码做四件事：`@SpringBootTest` 启动完整容器；`@ActiveProfiles("test")` 把数据源切到 `mall_test`；`@Import(MockMvcUtf8Config.class)` 注册 UTF-8 响应编码，否则断言中文会乱码；`@BeforeEach` 在每个用例前清库，保证用例之间互不干扰。

基类里还提供了 `newMerchant`、`newCategory`、`newProduct` 这类造数据的快捷方法，省得每个用例都手写一遍实体。

### 2. 一个集成测试长什么样

注册一个店家，然后断言返回结构：

```java
package com.mall.mall.controller;

import com.mall.mall.support.BaseIntegrationTest;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.http.MediaType;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

class MerchantControllerTest extends BaseIntegrationTest {

    @Test
    @DisplayName("注册成功返回 code=0，且密码以 BCrypt 密文入库")
    void 注册成功() throws Exception {
        mockMvc.perform(post("/api/merchants/register")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"username":"shop_a","password":"123456","shopName":"测试店铺"}
                                """))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.code").value(0));
    }
}
```

这里有三点值得留意：

1. **请求体用 Java 21 的文本块 `"""`**，不用手工拼字符串，也不用先转成对象再序列化，可读性最好。
2. **断言用 `jsonPath`**，直接精确到 JSON 里的某个字段，失败信息也看得懂。
3. **方法名可以用中文**（JUnit 5 支持），再配上 `@DisplayName`，测试报告一眼就知道哪条挂了。

### 3. 单元测试：只测不碰数据库的纯逻辑

用假的依赖对象替代 Mapper，重点验证「不该发生的事没有发生」：

```java
package com.mall.mall.service;

import com.mall.mall.common.BusinessException;
import com.mall.mall.dto.OrderCreateDTO;
import com.mall.mall.mapper.OrderItemMapper;
import com.mall.mall.mapper.ProductMapper;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.List;

import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private ProductService productService;

    @Mock
    private OrderItemMapper orderItemMapper;

    @Mock
    private ProductMapper productMapper;

    @InjectMocks
    private OrderService orderService;

    @Test
    @DisplayName("商品不存在时抛业务异常，且不写任何明细")
    void 商品不存在时抛异常() {
        when(productService.getById(999L)).thenReturn(null);

        OrderCreateDTO dto = new OrderCreateDTO();
        dto.setMerchantId(1L);
        dto.setBuyerName("张三");
        OrderCreateDTO.OrderItemDTO item = new OrderCreateDTO.OrderItemDTO();
        item.setProductId(999L);
        item.setQuantity(1);
        dto.setItems(List.of(item));

        assertThrows(BusinessException.class, () -> orderService.createOrder(dto));
        verify(orderItemMapper, never()).insert(any());
    }
}
```

单元测试的重点往往不是断言返回值，而是 **`verify`：确认不该发生的事没有发生**。上面这条用例真正想守住的是「商品不存在时一条明细都不许写」，`verify(..., never())` 才是它的主张。

## 五、关键点：事务回滚到底怎么测

这是整个方案里最需要想清楚的一处，写错了测试会绿得很虚假。

直觉做法是在测试类上加 `@Transactional`，让每个用例跑完自动回滚、互不污染。但这么一来，被测的 `OrderService.createOrder()` 上的 `@Transactional` 会**加入测试已经开好的事务**——于是你测到的其实是「测试事务的回滚」，而不是「业务事务的回滚」。业务代码里 `@Transactional` 即使被删掉，测试照样是绿的。

| 做法 | 数据是否干净 | 能否验证真实回滚 |
| --- | --- | --- |
| 测试类加 `@Transactional` | 自动回滚，干净 | 不能，测的是测试自己的事务 |
| 测试类不加，改用 `@BeforeEach` 清库 | 清库保证干净 | 能，走的是真实提交与真实回滚 |

**本项目的选择：集成测试不加 `@Transactional`，改用 `@BeforeEach` 清空测试库。**

代价是每条用例都要自己清场，好处是「库存不足时应回滚」这条用例才真正有意义：下单失败后直接去查库，确认订单和明细**确实一条都没落**——这是真实事务回滚给出的结果，而不是测试事务的假象。

## 六、Spring Boot 4 的写法变化（照抄 Boot 3 教程会报错）

Spring Boot 4 把测试相关注解按 web 层重新拆了包，写测试时最容易在这里卡住：

| 用途 | Boot 3 / 网上老教程 | Boot 4（本项目） |
| --- | --- | --- |
| MockMvc 自动配置 | `org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc` | `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` |
| 切片测试注解 | `org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest` | `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest` |
| 替换容器里的 Bean | `@MockBean`（已废弃） | `@MockitoBean`（`org.springframework.test.context.bean.override.mockito.MockitoBean`） |
| 测试 starter | `spring-boot-starter-test` | `spring-boot-starter-webmvc-test`（Boot 4 按 web 层拆分） |

判断方法：不确定某个注解在哪个包，就在 IDEA 里输入类名让它自动补全；或者去 Maven 本地仓库，按类路径搜一下 jar 里的 class 文件。

## 七、运行测试

| 命令 | 作用 |
| --- | --- |
| `mvn test` | 跑全部测试 |
| `mvn test -Dtest=OrderControllerTest` | 只跑某一个测试类 |
| `mvn test -Dtest=OrderControllerTest#下单成功` | 只跑某一个测试方法 |
| `mvn clean test` | 先清理产物再跑 |

跑测试前需要设置 `DB_PASSWORD`（和启动应用时一样，密码不进代码仓库）。

在 PowerShell 里：

```powershell
$env:DB_PASSWORD="你的MySQL密码"; mvn test
```

在 Git Bash 里：

```bash
DB_PASSWORD=你的MySQL密码 mvn test
```

### 手工回归脚本（可选）

自动化测试之外，`mall/http/mall-api.http` 提供了一份主链路的手工回归脚本。它使用 JetBrains HTTP Client 的 `.http` 格式：

- 在 IDEA Ultimate 中打开后，点击请求左侧的绿色箭头即可执行；
- IDEA 免费版没有 HTTP Client，可用官方免费 CLI `ijhttp` 原样运行，或用 VS Code REST Client（需删掉响应脚本、手工填变量）；
- 脚本按编号逐条执行，第 10 步取消订单后要重新下单才能继续支付，别直接整体运行。

执行顺序、变量传递、免费工具的具体用法和常见问题，见 [12-HTTP接口测试脚本使用说明](./12-HTTP接口测试脚本使用说明.md)。

## 八、常见坑

| 问题 | 原因与解决 |
| --- | --- |
| 断言中文时乱码或断言失败 | MockMvc 默认用 ISO-8859-1 解码响应体。用 `MockMvcBuilderCustomizer` 把默认响应编码设为 UTF-8（本项目已在 `MockMvcUtf8Config` 里配好，基类通过 `@Import` 引入） |
| 测试之间互相污染 | 没有隔离数据。用独立测试库 `mall_test` + `@BeforeEach` 清库 |
| 测试里验证不到回滚 | 测试类加了 `@Transactional`，业务事务加入了测试事务。验证回滚的用例不要给测试加事务 |
| 改用 `RANDOM_PORT` 后数据残留 | 真实端口意味着请求在**另一个线程**执行，测试事务管不到它。用 MockMvc |
| 报 `Table 'mall_test.order' doesn't exist` | 测试库没建表。执行 `mall/sql/05-测试库初始化.sql` |
| 找不到 `AutoConfigureMockMvc` | Boot 4 换了包名，见第六节 |
| 跑测试很慢 | `@SpringBootTest` 每次都要起容器。同一个测试类内的用例会复用容器，把相关用例写在同一个类里 |
