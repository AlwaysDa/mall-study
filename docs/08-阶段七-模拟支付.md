# 08 · 阶段七：模拟支付

> 目标：实现「模拟支付」链路，掌握支付状态流转、支付结果回调、订单状态联动。  
> 验收标准：下单 → 发起支付 → 模拟回调 → 订单变「已支付」，全链路跑通；且不能重复支付、不能支付已取消订单。

## 一、为什么要有「模拟支付」

真实支付会接入微信/支付宝，涉及签名、回调、对账等复杂流程。学习阶段我们用**模拟支付**来还原这套流程的核心逻辑，让你理解支付系统的设计思想，而不被第三方 SDK 细节淹没。

真实支付的核心链路：

```
用户下单 → 请求支付（生成支付单）→ 跳转第三方 → 支付成功
    → 第三方「回调」通知我们 → 校验 → 更新订单为已支付
```

模拟支付就复刻这个链路，把「第三方」换成我们自己的模拟接口。

## 二、支付状态流转

| 支付状态 | 值 | 含义         |
| ---- | - | ---------- |
| 未支付  | 0 | 订单刚创建      |
| 支付中  | 1 | 已发起支付，等待结果 |
| 已支付  | 2 | 支付成功       |
| 支付失败 | 3 | 支付失败       |

> 学习期可以简化：主要用「未支付 → 已支付」这条主链路，`支付中/失败` 作为扩展了解。

## 三、接口设计

| 功能     | 方法   | 路径                          | 说明          |
| ------ | ---- | --------------------------- | ----------- |
| 发起支付   | POST | `/api/pay/{orderId}`        | 返回模拟支付信息    |
| 模拟支付回调 | POST | `/api/pay/callback`         | 模拟第三方通知支付结果 |
| 查询支付状态 | GET  | `/api/pay/{orderId}/status` | 查询某订单的支付状态  |

## 四、实现思路

### 1. 发起支付（模拟）

真实场景会调用第三方接口生成支付单；这里直接返回「假支付单号 + 假支付链接」，并把订单置为「支付中」。

```java
@Service
public class PayService {

    private final OrderService orderService;

    public PayService(OrderService orderService) {
        this.orderService = orderService;
    }

    public PayResultVO createPay(Long orderId) {
        Order order = orderService.getById(orderId);
        if (order == null) {
            throw new BusinessException("订单不存在");
        }
        if (order.getStatus() != 0) {
            throw new BusinessException("只有待支付订单才能发起支付");
        }

        // 生成模拟支付单号
        String payNo = "PAY" + System.currentTimeMillis();
        // 真实场景：这里调用第三方支付接口，拿到支付链接
        String mockPayUrl = "https://pay.example.com/mock?payNo=" + payNo;

        order.setPayStatus(1);   // 支付中
        orderService.updateById(order);

        PayResultVO vo = new PayResultVO();
        vo.setPayNo(payNo);
        vo.setPayUrl(mockPayUrl);
        vo.setAmount(order.getTotalAmount());
        return vo;
    }
}
```

发起支付的返回 VO（文档前面用到 `PayResultVO`，这里补上定义）：

```java
package com.mall.mall.vo;

import lombok.Data;

import java.math.BigDecimal;

@Data
public class PayResultVO {
    private Long orderId;         // 订单ID
    private String orderNo;       // 订单号（方便对账时定位）
    private String payNo;         // 模拟支付单号
    private String payUrl;        // 模拟收银台链接
    private BigDecimal amount;    // 应付金额（取订单总额）
}
```

说明：真实场景中 `payNo` 和 `payUrl` 都由第三方支付平台返回，前端拿 `payUrl` 跳过去让用户付款。这里两个值都是我们拼出来的假数据，但字段与真实流程保持一致，以后替换成真实支付时不用改前端。

实际实现时 `orderId` / `orderNo` 也一并回填（从订单对象取），方便前端拿到支付信息后直接对应到订单、也方便排查问题时按订单号定位。

### 2. 模拟支付回调（核心）

真实场景：第三方支付成功后，会「回调」我们一个地址，我们**校验签名后**更新订单状态。这里模拟这个回调。

```java
@Transactional(rollbackFor = Exception.class)
public void handleCallback(PayCallbackDTO dto) {
    // 1. 根据订单ID找到订单（真实场景用支付单号/订单号定位）
    Order order = orderService.getById(dto.getOrderId());
    if (order == null) {
        throw new BusinessException("订单不存在");
    }

    // 2. 幂等校验：已支付的订单不能重复处理
    if (order.getPayStatus() == 2) {
        return;   // 已支付，直接忽略重复回调
    }
    if (order.getStatus() == 2) {
        throw new BusinessException("订单已取消，无法支付");
    }

    // 3. 根据回调结果更新状态
    if (dto.getSuccess()) {
        order.setPayStatus(2);   // 已支付
        order.setStatus(1);      // 订单已支付
    } else {
        order.setPayStatus(3);   // 支付失败
        // 订单回到待支付状态，可重新发起支付
        order.setStatus(0);
    }
    orderService.updateById(order);
}
```

回调 DTO：

```java
package com.mall.mall.dto;

import jakarta.validation.constraints.NotNull;
import lombok.Data;

@Data
public class PayCallbackDTO {
    @NotNull(message = "订单ID不能为空")
    private Long orderId;

    @NotNull(message = "支付结果不能为空")
    private Boolean success;   // true=支付成功 false=支付失败
}
```

查询支付状态的返回 VO（接口设计表里列了「查询支付状态」，这里补上它用的 VO —— 只暴露状态查询需要的字段，不把整个订单吐出去）：

```java
package com.mall.mall.vo;

import lombok.Data;

import java.math.BigDecimal;

@Data
public class PayStatusVO {
    private Long orderId;
    private String orderNo;
    private BigDecimal totalAmount;   // 应付金额
    private Integer status;           // 订单状态：0待支付 1已支付 2已取消
    private Integer payStatus;        // 支付状态：0未支付 1支付中 2已支付 3支付失败
}
```

PayService 里补一个查询方法：

```java
public PayStatusVO getPayStatus(Long orderId) {
    Order order = orderService.getById(orderId);
    if (order == null) {
        throw new BusinessException("订单不存在");
    }
    PayStatusVO vo = new PayStatusVO();
    vo.setOrderId(order.getId());
    vo.setOrderNo(order.getOrderNo());
    vo.setTotalAmount(order.getTotalAmount());
    vo.setStatus(order.getStatus());
    vo.setPayStatus(order.getPayStatus());
    return vo;
}
```

要特别注意区分两个状态：`status` 是订单状态（0待支付 1已支付 2已取消），`payStatus` 是支付状态（0未支付 1支付中 2已支付 3支付失败）。订单是「业务单据」，支付是「资金动作」，回调时两者在同一事务里一起更新，保持一致。

### 3. Controller

```java
package com.mall.mall.controller;

import com.mall.mall.common.Result;
import com.mall.mall.dto.PayCallbackDTO;
import com.mall.mall.service.PayService;
import com.mall.mall.vo.PayResultVO;
import com.mall.mall.vo.PayStatusVO;
import jakarta.validation.Valid;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/pay")
public class PayController {

    private final PayService payService;

    public PayController(PayService payService) {
        this.payService = payService;
    }

    // 发起支付
    @PostMapping("/{orderId}")
    public Result<PayResultVO> createPay(@PathVariable Long orderId) {
        return Result.success(payService.createPay(orderId));
    }

    // 模拟支付回调
    @PostMapping("/callback")
    public Result<Void> callback(@Valid @RequestBody PayCallbackDTO dto) {
        payService.handleCallback(dto);
        return Result.success();
    }

    // 查询支付状态
    @GetMapping("/{orderId}/status")
    public Result<PayStatusVO> status(@PathVariable Long orderId) {
        return Result.success(payService.getPayStatus(orderId));
    }
}
```

注意 `/callback` 和 `/{orderId}` 都是 POST：Spring 会优先匹配精确路径 `/callback`，其余才落到 `/{orderId}` 模板上，二者不冲突（和阶段五 `/page` 与 `/{id}` 是同一套匹配规则）。

## 五、核心设计思想（面试常考）

### 1. 幂等性

**支付回调可能被重复调用**（网络重试等）。如果没有幂等处理，同一个订单会被「支付」多次。上面的代码通过 `if (order.getPayStatus() == 2) return;` 保证重复回调不会重复处理。

> 「幂等」= 同一个操作执行多次，结果和执行一次相同。这是后端最重要的设计思想之一。

### 2. 回调校验（真实场景必须有）

真实支付中，回调必须校验**签名**，防止别人伪造回调篡改订单状态。学习期先略过签名，但要知道这个概念，进阶阶段可以自己实现一个简单的签名校验。

### 3. 状态机约束

任何状态流转前都要校验「当前状态是否允许流转」。上面的代码校验了：

- 只有「待支付」订单能发起支付
- 只有「未支付」的订单能回调为已支付
- 已取消的订单不能支付

## 六、完整支付链路验证

按顺序调用：

```
1. POST /api/orders            创建订单（status=0 待支付）
2. POST /api/pay/1             发起支付（pay_status=1 支付中，返回假支付链接）
3. POST /api/pay/callback      模拟回调 success=true
4. GET  /api/orders/1          查看订单，status=1 已支付，pay_status=2 已支付
```

再用 `success=false` 走一遍失败回调，观察订单回到「待支付」，可再次发起支付。

## 七、验收清单

- [ ] 待支付订单能发起支付，返回支付单号和模拟链接
- [ ] 支付回调 `success=true` 后，订单变为已支付
- [ ] 重复回调不会重复处理（幂等）
- [ ] 已取消订单发起支付被拦截
- [ ] 已支付订单再次发起支付被拦截
- [ ] 支付失败回调后订单回到待支付，可重试
- [ ] 能说出「幂等」是什么、为什么支付必须幂等

## 八、常见坑

| 问题         | 原因与解决                         |
| ---------- | ----------------------------- |
| 重复回调导致重复处理 | 加幂等校验，已支付直接返回                 |
| 回调改错订单状态   | 回调前校验订单当前状态是否合法               |
| 支付与订单状态不一致 | 用一个事务同时更新 pay_status 和 status |
| 回调接口被随意调用  | 真实场景要验签；学习期可先忽略但要知道风险         |
