# 11 · 测试用例清单

> 用途：把「该测什么」列成一张清单。写测试时照着挑，改完代码照着回归。
> 状态说明：**已实现** 表示功能已在项目里、主干用例也写成了自动化测试（当前 `mvn test` 共 58 条全绿）；**待实现** 表示功能还没写，用例先列出来占位，等该阶段做完再补测试。

这份清单不按代码文件组织，而按接口分组：一组用例对应一个 Controller，编号前缀固定，和测试类里的 `@DisplayName` 一一对应。

| 前缀 | 模块 | 接口前缀 |
| --- | --- | --- |
| C | 公共约定（所有接口） | — |
| M | 店家管理 | `/api/merchants` |
| K | 分类管理 | `/api/categories` |
| P | 商品管理 | `/api/products` |
| O | 订单管理 | `/api/orders` |
| Y | 模拟支付 | `/api/pay` |
| A | 鉴权与工程化 | 待实现 |

**怎么用这份清单：**

1. **补测试**：从对应模块的表里挑还没覆盖的行，编号写进 `@DisplayName`，测试方法名用中文。
2. **改代码后**：按第八节的回归清单走一遍，重点看表里标粗的那几条。
3. **用例失败**：先确认期望值本身写得对不对，再怀疑实现。清单里的期望结果是按接口契约定下的，实现向它看齐。

清单里有四条边角用例（M-7 账号不存在、M-11 默认分页、P-7 按状态过滤、O-10 按店家过滤）暂未自动化，可以先用 `mall/http/mall-api.http` 手工覆盖。

## 一、公共约定（所有接口都要满足）

这几条是「全局规矩」，写任何接口的测试时都该顺手验一下。

| 编号 | 用例 | 期望结果 |
| --- | --- | --- |
| C-1 | 正常请求 | HTTP 200，返回体为 `{code:0, message:"success", data:...}` |
| C-2 | 业务异常（如查不到、库存不足） | 返回体 `code` 非 0，`message` 是可读的中文提示 |
| C-3 | 访问不存在的路径 | HTTP 404，返回体 `code=404`、`message="接口不存在"` |
| C-4 | 请求体字段不合法 | 返回 `code=400` + 具体字段提示（如「账号不能为空」），不进入业务逻辑 |
| C-5 | 列表类接口无数据 | 返回 `data: []` 或分页 `records: []`，而不是 `null` |

> C-4 是后来补上的：全局异常处理器新增了 `MethodArgumentNotValidException` 的处理，取第一个字段错误信息返回 `code=400`。在此之前，校验失败会落到通用异常兜底，返回 `code=500`「系统内部错误」。

### 写测试时暴露出的两个代码缺口（已修复）

| 编号 | 问题 | 影响 | 状态 |
| --- | --- | --- | --- |
| G-1 | 下单只校验商品，**不校验 `merchantId` 是否存在** | 传入不存在的店家也能下单成功，订单会带一个悬空的 `merchantId` | ✅ 已修复 |
| G-2 | 参数校验失败返回 `code=500`「系统内部错误」 | 调用方看不出是哪个字段不合法（对应 C-4） | ✅ 已修复 |

这两条不是测试写错了，是测试帮忙找出来的代码问题。修复方式：

- **G-1**：`OrderService` 注入 `MerchantService`，在 `createOrder` 开头补一次店家存在性校验（与 `ProductService.createProduct` 的做法一致），不存在则抛「店家不存在」。事后补了用例 **O-15**。
- **G-2**：`GlobalExceptionHandler` 新增 `MethodArgumentNotValidException` 处理，取第一个字段错误信息返回 `code=400`。同时把 M-3、M-4、P-13、O-6、Y-9 的断言从「`code` 非 0」收紧为「`code=400` + 具体字段提示」。

## 六、模拟支付（已实现）

接口前缀 `/api/pay`。自动化测试见 `src/test/java/com/mall/mall/controller/PayControllerTest.java`。

有个前提要说清楚：本项目**没有独立的支付流水表**，支付状态直接记在 `order.pay_status` 上（0 未支付、1 支付中、2 已支付、3 支付失败）。所以下面断言的是订单上的两个状态字段，而不是某条「支付流水」记录。真实支付系统通常会有独立的支付单表，这里从简。

| 编号 | 用例 | 期望结果 |
| --- | --- | --- |
| Y-1 | 待支付订单发起支付 | 返回模拟支付单号与链接，订单 `pay_status=1`（支付中）、`status` 仍为 0 |
| Y-2 | 对不存在的订单发起支付 | 被拦截，提示「订单不存在」 |
| Y-3 | 已支付订单再次发起支付 | 被拦截，提示「只有待支付订单才能发起支付」 |
| Y-4 | 已取消订单发起支付 | 被拦截（`status=2`，同上一条拦截） |
| Y-5 | 回调 `success=true` | 订单 `status=1`（已支付）、`pay_status=2`（已支付） |
| Y-6 | 回调 `success=false` | 订单回到 `status=0`（待支付）、`pay_status=3`（支付失败），可重新发起支付 |
| Y-7 | **重复回调（幂等）** | 第二次调用**静默返回不报错**，两个状态字段都保持最终值不变 |
| Y-7b | 已支付订单收到失败回调 | 被幂等拦截，不会被改回未支付 |
| Y-8 | 对已取消订单回调 | 被拦截，提示「订单已取消，无法支付」 |
| Y-9 | 回调缺少 `success` 参数 | 返回 `code=400` + 「支付结果不能为空」 |
| Y-10 | 查询支付状态 | 返回 `status` / `payStatus` / `totalAmount` |

> Y-7 是这一阶段最该测的一条：支付平台的回调会因为「没收到成功响应」而反复重试，幂等没做对就会重复处理。注意本项目对重复回调的处理是**静默忽略**（直接 `return`），而不是抛异常，所以用例要断言「HTTP 200 且状态未变」，别断言成抛错。

## 八、回归清单（每次较大改动后跑一遍）

1. `mvn test` 全绿，这是自动化回归。
2. 用 `mall/http/mall-api.http` 手工走一遍主链路：注册 → 登录 → 建分类 → 建商品 → 入库 → 下单 → 查详情 → 取消。
3. 重点确认三条最容易回归的：**下单扣库存正确**、**库存不足无残留**、**取消能回补库存**。
