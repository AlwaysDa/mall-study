# 11 · 测试用例清单

> 用途：把「该测什么」列成一张清单。写测试时照着挑，改动代码后照着回归。  
> 状态说明：**已实现** = 功能已在项目里，主干用例已写成自动化测试（`mvn test` 全绿）；**待实现** = 功能还没写，先把用例列出来，等该阶段做完再补测试。  
> 清单里少量边角用例（如 M-7 账号不存在、M-11 默认分页、P-7 按状态过滤、O-10 按店家过滤）暂未自动化，可先用 `mall/http/mall-api.http` 手工覆盖。

## 一、公共约定（所有接口都要满足）

这几条是「全局规矩」，写任何接口的测试时都该顺手验一下。

| 编号  | 用例              | 期望结果                                                  |
| --- | --------------- | ----------------------------------------------------- |
| C-1 | 正常请求            | HTTP 200，返回体为 `{code:0, message:"success", data:...}` |
| C-2 | 业务异常（如查不到、库存不足） | 返回体 `code` 非 0，`message` 是可读的中文提示                     |
| C-3 | 访问不存在的路径        | HTTP 404，返回体 `code=404`、`message="接口不存在"`             |
| C-4 | 请求体字段不合法        | 请求被拒绝（`code` 非 0），不进入业务逻辑                             |
| C-5 | 列表类接口无数据        | 返回 `data: []` 或分页 `records: []`，而不是 `null`            |

> 说明：C-4 目前由通用异常兜底处理，返回的是 `code=500`「系统内部错误」，提示不够精确。让它返回 `code=400` + 具体字段错误信息，是阶段八「参数校验异常返回统一错误信息」这一条待办。

## 五、订单管理（已实现）

接口前缀 `/api/orders`。这是本项目的核心模块，用例最多。

| 编号   | 用例          | 请求                       | 期望结果                                   |
| ---- | ----------- | ------------------------ | -------------------------------------- |
| O-1  | 下单成功        | `POST /`                 | `code=0`；订单、订单明细各生成一条；商品库存**精确扣减**对应数量 |
| O-2  | 多商品下单       | `POST /`（items 含两条）      | 订单总额 = 各明细小计之和；两条明细都落库                 |
| O-3  | **库存不足时回滚** | `POST /`（quantity 大于库存）  | `code` 非 0；**订单表与明细表都没有新记录**（事务回滚）     |
| O-4  | 商品不存在       | `POST /`（productId 不存在）  | `code` 非 0，提示「商品不存在」；不写库、不扣库存          |
| O-5  | 明细是快照       | 下单后修改商品名与价格，再查详情         | 明细里的 `productName`/`price` 仍是**下单时**的值 |
| O-6  | 下单明细为空      | `POST /`（items 为空数组）     | 请求被拒绝，不写库                              |
| O-7  | 订单号唯一       | 连续下两单                    | 两个 `orderNo` 不相同                       |
| O-8  | 订单详情        | `GET /{id}`              | `code=0`，`data.items` 含明细列表            |
| O-9  | 查询不存在的订单    | `GET /{id}`              | `code` 非 0，提示「订单不存在」                   |
| O-10 | 分页按店家过滤     | `GET /page?merchantId=x` | 只返回该店家的订单                              |
| O-11 | 分页按状态过滤     | `GET /page?status=0`     | 只返回待支付订单                               |
| O-12 | 取消待支付订单     | `PUT /{id}/cancel`       | `code=0`；`status` 变为 2；**库存回补**到下单前的数量 |
| O-13 | 取消已支付订单     | 先把 `status` 改为 1，再取消     | `code` 非 0，提示「只有待支付订单才能取消」；状态与库存都不变    |
| O-14 | 重复取消        | 取消两次                     | 第二次被拦截（此时状态已是 2）                       |

### 写测试时暴露出的两个缺口

| 编号  | 问题                                | 影响                                    |
| --- | --------------------------------- | ------------------------------------- |
| G-1 | 下单只校验商品，**不校验 `merchantId` 是否存在** | 传入不存在的店家也能下单成功，订单会带一个悬空的 `merchantId` |
| G-2 | 参数校验失败返回 `code=500`「系统内部错误」       | 调用方看不出是哪个字段不合法（对应 C-4，阶段八修复）          |

这两条不是测试的问题，是测试帮忙找出来的代码问题。G-1 可以在 `OrderService.createOrder` 里注入 `MerchantService` 补一次存在性校验；G-2 需要在全局异常处理器里加 `MethodArgumentNotValidException` 的处理。

## 七、鉴权与工程化（阶段八 · 尚未实现）

| 编号  | 用例              | 期望结果                                             |

| A-1 | 登录后拿到 token     | 返回体含 token，且能被服务端校验通过                            |

## 八、回归清单（每次较大改动后跑一遍）

1. `mvn test` 全绿（自动化回归）。
2. 用 `mall/http/mall-api.http` 手工走一遍主链路：注册 → 登录 → 建分类 → 建商品 → 入库 → 下单 → 查详情 → 取消。
3. 重点确认三条最容易回归的：**下单扣库存正确**、**库存不足无残留**、**取消能回补库存**。
